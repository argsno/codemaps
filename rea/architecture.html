一入门：这是什么

1.1 一句话与它解决的问题

REA（Reverse Engineer Anything）是一个本地运行的逆向工程工具：同时提供 MCP server 与 CLI 两个入口，让 AI agent 或终端用户对本地目标（二进制、Electron 应用、网页、APK、固件、抓包……）做分析，并让每一条结论都带着「证据」与「不确定性」。 事实 README.md:6-8,59-61；package.json:5

它要解决的问题可以概括成三句话：

① 让 agent「看得懂」目标

没有源码时，功能、协议、数据结构只存在于二进制与运行时里。REA 把它们变成结构化、可引用、可回放的分析结果，交给 agent 去解释与复刻。

② 把十几种引擎统一成一套语义

Hopper / Ghidra / IDA / JADX / Playwright / TShark……每个引擎的协议、生命周期、错误形态都不同。REA 用统一的 Provider 端口、证据模型与会话规则把它们抹平。

③ 让结论可信、可追溯

每条结论是一条 Evidence 记录：谁（provider）、对哪个目标（artifact 摘要）、做了什么（operation+参数）、看到什么（结果）、有什么局限（limitations），以及它来自真实观察还是快照回放。

它不是

不是反编译器本身（引擎是别人的）、不是云服务（本地运行、不上传目标）、也不是自动化攻击工具——它只做「理解」，并且把「没弄明白的部分」显式记录下来。 事实 README.md FAQ；DISCLAIMER.md

1.2 名词表

先看这张表，后面所有章节都能对上号。

名词含义
逆向工程在没有（或缺少）源码的情况下理解软件：静态分析读二进制，动态分析观察运行行为。REA 两者都做。
伪代码 / 汇编反编译产物（接近 C 的伪代码）与机器指令的文本形式；REA 主要返回这两种「代码证据」。
符号 / 引用（xref）函数与数据的名字，以及「谁调用了谁、谁引用了哪块数据」的关系。是追溯调用链的基础。
MCPModel Context Protocol：agent 调用外部工具的标准协议。REA 的 MCP server 通过 stdio 与 agent 通信，暴露一批 tools 与 prompts。
Tool Contract（工具契约）一个 MCP 工具的单一事实源：名字、描述、输入/输出 schema、副作用声明、是否返回目标内容、示例。代码里就是一个 ToolContract 对象。
Provider（供应商）某一类分析能力的适配器，如 Hopper、Ghidra、IDA、浏览器、JADX。实现统一端口：能声明能力、检查可用性、解析分析剖面、创建客户端执行操作。
Bridge（桥）注入到外部工具进程内部运行的小程序（Python / Java），把引擎的 API 翻译成 REA 能用的请求-响应协议。
Session（会话）REA 进程内「当前分析目标」的持有者。同一时刻只有一个活跃目标，所有工具调用都挂在它上面。
Evidence（证据）一条结构化的观察记录，带语义 ID（内容哈希）、置信度、权威等级、局限与源码位置。它是 REA 的「货币」：工具返回它，账本保存它。
ResidualUnknown（残余未知）显式登记的「还没搞清的事」，带状态与修订号。防止未知被静默当作「不存在」。
Snapshot（快照）对某个目标 + 分析剖面，把已发生的查询结果与证据打包，可导入/导出/回放。回放会明确标注「本次未重新执行引擎」。
Analysis Profile（分析剖面）同一个目标的两次分析可能不同（引擎版本、语言选项、种子文件……）。剖面记录这些参数，参与缓存与快照的身份判定。
Capability / AvailabilityProvider 声明「我会哪些操作」（Capability）与「我现在能不能用」（Availability，例如缺工具、平台不支持）。

1.3 怎么跑起来

两种用法：让 agent 用（注册 MCP），或自己在终端用（CLI）。

# 给 agent 用：注册 MCP server 并安装配套 skill（支持 Claude Code / Codex / Cursor 等约 25 个客户端）
npx rea-agents setup

# 终端用：全局安装后使用 rea 命令
npm install --global rea-agents
rea --help

# 不走安装，直接跑一条命令（示例：静态分析一个 JS/Electron 应用目录或 ASAR）
npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json

出处：README.md:65-118；package.json:40-43

  • 运行环境：Node.js ^22.19 || ^24.11 || >=26 + npm。 事实 package.json:44-47
  • 外部工具自带（BYO）：Hopper / Ghidra / IDA / JADX / Apktool / TShark / WABT / pwntools 等都不由 REA 安装；只有 Hopper 可以在 setup 时选择安装且必须经过批准。 事实 AGENTS.md:24-30；README.md:160-198
  • 纯静态能力不需要外部引擎：JavaScript/Electron 静态分析、.NET、Go、Rust、Flutter 等由 REA 自己解析。 事实 README.md:167-183

二设计：为什么长这样

2.1 分层与依赖方向

每个目录的规模和职责如下（文件数为粗计，用于感受重心）：

层规模职责
src/domain/568 文件纯函数、无副作用。Evidence 与错误模型、目标身份、快照格式、比较与图算法、未知项。整个项目的「语义字典」。
src/contracts/87 文件对调用者的输入/输出 schema（Zod）、工具契约（36 个契约数组汇入 TOOL_CONTRACTS）、错误 schema。是 MCP 与 CLI 的公共表面。
src/application/319 文件跨 provider 的共享工作流：会话、证据、缓存、安装、诊断、各领域服务。
src/composition/33 文件唯一的生产装配点：工厂、惰性可选 provider、生命周期接线。
src/*/（provider）合计 400+ 文件各引擎适配器：hopper 30、ghidra 68、browser 124、ida 33 …… 实现统一端口。
src/cli/ + src/server/50 + 93两个交付适配器：命令注册与 MCP 工具注册。
src/process/ + src/windows/72 + 若干进程与资源所有权基座（见 §4.6）。

为什么要这么切？ 因为分析能力会不断新增（十几年里攒下二十多种目标类型），而「证据要可信、资源要清理干净、结论要可复现」这几条不变量必须只有一份实现。推断

2.2 双适配器与唯一装配点

CLI 与 MCP 不是两套系统，而是同一系统的两个门面：两边都走 createBinarySession() 构造同一个会话实现。装配点的注释把这件事写得很直白：

// src/composition/binary.ts
// Compose the target-switching runtime shared directly by CLI and MCP adapters.
// This is the sole production wiring point, so both adapters share identical
// provider selection, profile, lifecycle, and Evidence semantics.

实践含义：你在任一门面看到的行为（选择哪个 provider、缓存怎么命中、错误怎么呈现）都必须在另一门面同样成立。新增能力时，先接 application 端口，再分别注册 CLI 命令与 MCP 工具。 事实 src/composition/binary.ts:19-26；src/cli.ts:87-148；src/server/createServer.ts:439-582

2.3 五条设计原则

这五条贯穿全部代码，后面每个机制都是它们的实例。它们是理解 REA「为什么这么做」的钥匙。

原则含义可验证的证据
Fail-closed
不确定就拒绝		 宁可报错或标未知，也不猜。多个 provider 都可用时报 ambiguous 而不是按优先级挑一个；无法证明所有权就保留并重试，不当作已清理。 AnalysisProviderRegistry.ts:185-300；AGENTS.md:41-44
证据可追溯
结论必须能回放		 每条结论是一条 Evidence：谁、对什么、做了什么、看到什么、有什么局限。回放旧结果时显式降级声明。 domain/evidence.ts:96-205；AnalysisSnapshotCache.ts:250-270
一个资源一个 owner
清理失败要保留		 资源的所有权明确；清理失败的资源留在 pending 里下次重试，并在错误上标 cleanupIncomplete，绝不当成成功。 BinarySession.ts:494-520；analysisErrorBase.ts:55-100
省 token 优先
先省 agent 的上下文		 性能按「agent token → 分析时间 → CPU/内存」排序：返回最小充分答案，提供分页与保留证据引用，而不是把大结果一次性灌给模型。 AGENTS.md:60-72；server/toolResult.ts
配置只增不改
幂等 + 有备份		 setup/卸载对用户配置文件做「先备份、原子写、能回滚」的幂等变更。 SetupClientConfiguration.ts:219-239；AGENTS.md:24-30

三主流程：从启动到结果

3.1 启动（MCP 与 CLI）

包入口是一个分发器，按参数把进程交给两条路径之一：

rea mcp | rea --mcp   →  dist/mcp/main.js        （源码 src/main.ts）
rea mcp doctor        →  额外加载 dist/cli-runtime/mcpDoctor.js
其它参数              →  dist/cli-runtime/cli.js  （源码 src/cli.ts）

出处：package.json:40-43；scripts/rea.mjs（全文）

MCP 启动序列 事实 src/main.ts:50-95

  1. 冻结环境快照

    snapshotEnvironment(process.env)——运行期间配置不再漂移（Windows 下还处理大小写不敏感的键语义）。

  2. 解析配置

    parseConfig 用 Zod 校验 REA_* 环境变量；失败只提示「哪个设置不合规」，不回显值。

  3. 构造会话

    createBinarySession(config, logger, environment)：注册 Hopper / Ghidra / IDA 三个深 provider 与一组惰性辅助 provider（此时不启动任何引擎）。

  4. 可选：打开预置目标

    若配置里指定了目标路径，调用 session.open()；失败则打印错误并退出，且把已分配的资源清理掉。

  5. 启动传输层

    serveStdio(() => createServer(...))：SDK 每次要 server 时现场构造一个（SDK 会丢弃探测用的实例，所以实例集合被跟踪、统一关闭）。

  6. 登记关闭钩子

    SIGINT / SIGTERM / stdin EOF / close 都走同一套幂等清理：关传输 → 关会话 → 释放 provider。

CLI 启动序列 事实 src/cli.ts:63-148

构造一个 incur Cli 实例，注册 30+ 组命令（setup/doctor、核心分析、各 provider 平台命令、浏览器与运行时观测、证据与产物）。命令执行时按需构造 createDirectAnalysis(environment)——分析命令各自获取并关闭自己的会话，因此 CLI 与 MCP 的差别只在「谁持有会话生命周期」。

注意

CLI 的 mcp 子命令不会走到这里——分发器在加载 CLI 之前就把它劫持给了 MCP 运行时，避免 CLI 框架在启动时初始化引擎。事实 scripts/rea.mjs:9-14；src/cli.ts:60-63 注释

四核心机制逐条拆解

这一章是「精通」部分的基础。每条机制都回答同一个问题：它在防什么？ 读完之后，你应该能解释代码里那些看起来"过度小心"的注释。

4.1 BinarySession：唯一活跃目标

问题：分析引擎的状态很重（打开的目标、临时数据库、编辑器光标）。如果允许多个目标并存或并发切换，任何一次切换都可能让正在跑的分析引用已经消失的资源。

做法：进程内只允许一个活跃绑定，所有目标切换串行化，切换时先"排干"在途调用。 事实 src/application/binary/BinarySession.ts

机制行为
单一绑定只保留一份 {target, client, profile, route, runId}；没有绑定时的调用返回可解释的选择失败，而不是"随便找一个"。
切换串行化每次生命周期操作分配一个 generation；切换只等待"本次之前已受理"的调用（#drainCalls），之后的调用排在切换后面。
失败回滚切换失败时用同一路由重建旧目标（新 client + 健康检查）；恢复也失败则把两个错误合成一个 cleanupIncomplete 错误。
保留快速路径同目标同剖面重开时，先探测底层子进程健康快照；只有 idle / busy 才算活着——unknown 从来不是"健康"的证据。
外部变异纪律任何可能改动目标的外部命令：先失效缓存与快照，执行，然后退役当前目标（要求重新打开）。Ghidra 活跃时直接拒绝这类操作。
关闭语义close() 清空会话记录；closeWithSnapshot(path) 在同一个锁里完成「排水 → 导出快照 → 写文件 → 关闭」。
深挖：为什么"health 返回 ok"不能证明 provider 还活着？

因为绑定给会话的 client 往往是一个复合对象（CompositeProvider），它的 health 是无条件成功的——它不真正触达子进程。所以快速路径改看 operationHealthSnapshot()，这个信号才来自真正实例化的子进程。事实 BinarySession.ts:869-895 注释

另外三个状态被刻意排除：exited（已死）、unreachable（够不到）、not_started（启动从未完成——在 Hopper 超时场景下，client 还持有阻塞下一次启动的资源，把它当作活着会跳过退役流程，把"卡死"传给下一次分析）。推断：这是本文件里信息量最大的一段注释，值得原样读一遍。

4.2 Provider 选择：确定性、无回退

问题：同一台机器上可能同时装着 Hopper 和 Ghidra。如果"按优先级挑一个"，用户看到的结论就取决于安装顺序或注册顺序——这会让结论不可复现。

做法：注册表只做确定性选择，并把"候选状态"完整暴露给调用方。 事实 src/application/binary/AnalysisProviderRegistry.ts

环节规则
注册期校验provider ID 唯一、能力声明的 provenance 必须与自身 identity 一致、同一 operation 不得重复声明——违反直接抛 TypeError（启动就失败，不留到运行期）。
三档来源request（调用方显式指定）＞ environment（REA_ANALYSIS_PROVIDER）＞ auto-single-candidate（自动，且仅当恰好一个候选可用）。
歧义即报错自动模式下有多个可用候选 → ambiguous 错误（附每个候选的拒绝原因与诊断），让调用方显式选，而不是替它决定。
目标不支持能力可用但目标格式/架构不支持 → target_unsupported，同样列出原因（例如"Ghidra v1 无法在导入 universal Mach-O 时强制选定架构，请先瘦身"）。
路由组合选中的"深 provider"与若干"辅助 provider"合成一个复合 client；深/辅两边的 operation 集合必须不相交，否则启动即报错。
无绑定兜底没有任何深 provider 可用时给出一个空 client：health 正常，其余操作返回「本 provider 集未声明此操作」，而不是崩溃。

4.3 快照缓存：什么能回放

问题：同一次调查里，agent 会反复问同一件事（同一个函数的伪代码、同一批引用）。重复调用外部引擎既慢又贵；但错误的复用会让结论失真——尤其当底层数据可能变过。

做法：只有满足一组严格条件的调用才进入会话内缓存；回放时显式标注来源。 事实 src/application/binary/AnalysisSnapshotCache.ts

  • 键：目标身份 + 分析剖面 + operation + 参数（规范化后哈希）。三者任一变化，缓存不成立。
  • 可缓存判定：操作不是有状态类（health/current_*/goto_*/list_documents）、不依赖隐式光标（除非显式传了地址）、声明 mutatesArtifact === false 且不改权限、缓存策略不是 live。
  • 失效：声明会改动目标的操作在下发之前就让缓存失效——"一次失败的回包无法证明已下发写入被回滚"；外部变异命令同样触发失效（见 4.1）。
  • 上限：primitive 与 workflow 条目合计 10000 条；满了就停止记录（而不是淘汰，保证确定性）。
  • 回放标注：回放结果会附加一条 limitation：「Loaded from a local REA analysis snapshot; this call did not re-run the provider.」并把 subject 的本地路径重绑到当前目标。
  • 不记录截断结果：标记为 referencesTruncated 的结果不写缓存——否则回放会把"截断"当"完整"。

快照还能整体导出/导入（exportAnalysisSnapshot / importAnalysisSnapshot），导入时校验目标与剖面匹配，不匹配直接拒绝（AnalysisSnapshotMismatchError）。 事实 src/application/binary/BinarySessionRecords.ts

4.4 Evidence：证据即身份

问题：如果结论只是"一段 JSON"，agent 无法区分它是真实观察、快照回放还是推测，也无法在后续调用中安全引用它。

做法：把每次观察铸成一条不可变、可校验、可引用的记录。 事实 src/domain/evidence.ts

字段组内容与作用
subject（对象）目标身份的规范化投影：sha256、格式（elf/pe/mach-o/asar/…）、架构；local_path 与显示名不参与身份，所以换路径不会改变证据 ID。
provenance（来源）provider 的 id/name/version、analysis_profile（分析剖面）、environment（执行环境）。
observation（观察）operation、parameters、raw_result（引擎原始表示）、normalized_result（REA 归一化结果）。
epistemics（认识论）confidence：observed / derived / inferred；authority：shipped-artifact / controlled-replay / historical-reference / external-service / analyst-inference。
limits（边界）limitations 列表、relationship_coverage（关系查询的覆盖率，缺失即 unknown）、locations（地址/文件偏移等源码位置）、evidence_links（派生自哪些证据）。

身份是怎么算的：evidence_id = "ev_" + sha256(canonical(语义投影))。解析时重算哈希并拒绝被篡改的 ID；比较时忽略显示字段。证据一旦记录即深冻结（用弱表登记不可变实例，避免重复校验大对象）。 事实 evidence.ts:180-260

账本纪律：记录是幂等的——同 ID 同内容算重复，同 ID 不同内容直接报冲突；整包导入先整体校验再原子合并。 事实 src/application/investigation/EvidenceLedger.ts:31-140

错误也是证据的一部分

分析失败不会丢掉已完成的部分：错误对象可以携带 partialObservation（失败前已获得的观察），交付层会把它作为带引用的部分结果返回；错误本身是 27 种稳定 tag 的联合类型，携带 diagnostics、捕获输出、清理状态，全部经统一投影后才会出现在协议里。 事实 src/domain/analysisErrorBase.ts:4-31；src/server/contractToolHandler.ts:52-70

4.5 ResidualUnknown：未知是一等公民

问题：逆向里最常见的事故不是"没查到"，而是"没查到被当成不存在"。一旦结论写成"目标没有这个功能"，而实际上是没查到，后续所有推理都会建立在错误前提上。

做法：未知项是一个有状态、可查询、可解冻的实体，且必须挂在一条"变异证据"上。事实 src/domain/residualUnknown.ts；EvidenceLedger.ts:170-256

  • 字段：unknown_id、状态、严重度、领域、修订号与修订摘要、解决方案（含 verified 处置）。
  • 更新用乐观并发：必须带 expected_revision，不匹配即 revision-conflict。
  • 登记与解决都要求附一条证据，且该证据必须真实存在于账本（或与未知项一起原子写入）。
  • 查询分页稳定：按 ID 排序，带 next_offset。

推断：这套机制让 agent 的"我不确定"有地方可写，也让用户的复查有据可依——它是整个项目"证据文化"的一部分。

4.6 进程所有权：证明"这是我的"

问题：REA 要替用户启动引擎（Hopper、Ghidra、JADX、pwntools……）。清理时如果杀错进程，后果严重；如果漏杀，会留下孤儿进程。PID 会被复用，路径可以被伪造。

做法：用一组可验证的信号建立所有权，清理失败保留所有权重试。 事实 src/process/ProcessOwnership.ts

手段说明
run token给每个子进程注入唯一环境变量 REA_PROCESS_RUN_ID；清理与巡检前读回进程环境比对。可读但不匹配 = 不是我的；不可读 = 记 environment-unreadable（是证据，不是"跳过"）。
身份夹逼读 token 前后各取一次进程启动身份（Linux 用 stat 的 starttime 字段，Darwin 用原生 helper），中途变化即判定失败。
基线对照启动前记录 pid→身份 基线，扫描时丢弃"身份没变过"的进程。
退场竞态只有当新快照证明 PID 已消失，才允许把不匹配归因于"进程已退出"；只有"PID 不存在"能消解不可读。
清理重试清理失败 → 资源留在 pending，下一次关闭/操作前重试；错误上标记 cleanupIncomplete 并保留资源清单。
Windows 三件套原生 Node-API 插件提供 Job Object 进程所有权、按 DACL 证明的私有目录、以及防重解析点（符号链接）的路径准入；明确声明"不由 taskkill/chmod 推断"。
深挖：为什么 Windows 必须写原生插件？

POSIX 上可以用 mkdtemp（owner-only 目录）和进程组表达所有权；Windows 上没有等价可证明的语义。原生插件做的是：CREATE_SUSPENDED 创建进程后，用 PROC_THREAD_ATTRIBUTE_JOB_LIST 原子地把进程放进 Job Object（并用 KILL_ON_JOB_CLOSE 保证宿主消失时子进程一起死），创建目录时安装私有 DACL，并用卷序列号 + 文件 ID 做路径准入；句柄带类型标签，伪造或序列化的句柄拿不到权限。 事实 native/windows/src/{process.cc,filesystem.cc,addon.cc}

4.8 MCP 交付：预算、不截断、不可信标记

问题：agent 的上下文有限；大函数伪代码可能几十万字符。另外，目标内容（字符串、注释、脚本）可能包含针对 agent 的注入指令。

做法：交付层（src/server/toolResult.ts + EvidenceMcpServer.ts）执行三条硬规则：

  • 绝不静默截断：超出预算（REA_MCP_MAX_RESPONSE_BYTES，默认取 SDK 的 stdio 缓冲上限）时，返回一个「分析资源约束错误」，附带恢复路径——用分页 continuation 读保留证据、导出完整证据、或调大预算。事实 toolResult.ts:150-215
  • 不可信标记：所有会返回目标内容的工具，其结果（包括失败）都带 _meta.provenance.untrusted_content；server 的 instructions 明确要求 agent 把目标内容当数据、遇注入要报告用户。事实 src/server/createServer.ts:145-147；EvidenceMcpServer.ts:230-260
  • 广告面与执行面分离：compact 档位下压缩对外广告的输入 schema，但注册给 SDK 的规范 schema 不变；关闭 outputSchema 广告时本地仍然校验结果。事实 EvidenceMcpServer.ts:88-130
深挖：连"错误太大"都被保留成证据

如果一条错误回复本身就超出预算，传输夹层会把完整的错误投影存进证据账本，再把回复换成一条小错误，里面带 evidence_reference 和修复建议（"导出这份保留错误"或"重启时调大预算"）。也就是说：在 REA 里，连失败信息都有可追溯的落点。 事实 EvidenceMcpServer.ts:262-330

七精通：扩展与陷阱

7.1 新增一个 Provider 的清单

假设你要接入一个新引擎（比如某个没被支持的反汇编器）。按依赖方向从内到外做：

  1. 定义契约与类型

    在 src/contracts/ 增加工具契约（名字/描述/输入输出 schema/effects/returnsTargetContent/示例），并接入 TOOL_CONTRACTS 聚合。工具描述要写清"答案是什么、覆盖什么、局限是什么"。

  2. 实现领域归一化

    引擎输出 → REA 的统一结果形状；遇到不确定的语义，宁可标 unknown，不要猜（§4.5）。

  3. 写 Provider 与 Configuration

    实现 identity / capabilities / inspectAvailability / inspectTargetSupport / resolveAnalysisProfile / createClient；工具发现集中在 XConfiguration.ts，路径类配置强制绝对路径。

  4. 客户端与进程所有权

    客户端负责传输与协议校验；启动子进程必须走 src/process/（owner 化进程组 + run token + 超时 + 清理重试）。

  5. 装配到 composition

    在 src/composition/ 写工厂（构造期零 I/O），可选能力用惰性加载，失败降级为工具级不可用。

  6. 注册两个门面

    MCP：在 src/server/register*Tools.ts 绑定契约；CLI：在 src/cli/ 注册命令并复用同一 application 服务。

  7. 申报可用性

    把"平台 + 环境变量 + 依赖缺失"折算进 availability 投影，并写好人类可读的修复建议（CapabilityInventory 风格）。

  8. 测试与真实验证

    同目录单测 + 边界测试；再加一条真实环境 verify:*，否则不算接入完成。
